# Reconstruction model comparison

The user reported that two further Hunyuan reconstructions do not resemble the approved character images geometrically. One appears open above the hair. No postprocessing of the returned mesh is proposed as a remedy; the reconstruction model itself needs comparison against alternatives on the same approved image set.

The three locally available Hunyuan GLBs have roughly 440–466k triangles and no semantic rig. A container and topology inspection cannot establish visual likeness or whether the visible crown is satisfactorily filled. The user's visual report is the relevant evidence for those failures.

| Model              | Fal endpoint                                                            | Image inputs used                                                 | GLB output                                       |
| ------------------ | ----------------------------------------------------------------------- | ----------------------------------------------------------------- | ------------------------------------------------ |
| Hunyuan 3D Pro 3.1 | [API](https://fal.ai/models/fal-ai/hunyuan-3d/v3.1/pro/image-to-3d/api) | All six approved views                                            | `model_glb`                                      |
| Tripo H3.1         | [API](https://fal.ai/models/tripo3d/h3.1/multiview-to-3d/api)           | Front, left profile, back, right profile, in the documented order | `model_urls.glb`, or a verified GLB `model_mesh` |
| Meshy 7.1          | [API](https://fal.ai/models/meshy/v7.1/multi-image-to-3d/api)           | The same four cardinal views                                      | `model_glb`                                      |
| Hi3D Portrait 2.1  | [API](https://fal.ai/models/hitem3d/hi3d/multi-view-to-3d/api)          | The same four cardinal views, using named fields                  | `model_mesh`                                     |

Tripo accepts 2–4 images and requires the order front, left, back, right. Meshy accepts at most four images, so the two 45° views are excluded deliberately rather than silently dropped by the provider. Hunyuan retains all six. The four-view comparison is therefore **not an equal-input benchmark**; it tests which available service yields a better usable head under its documented constraints.

The main measured failure in earlier models was **facial identity loss between the approved image set and the raw 3D reconstruction**. The mesh often had sufficient structural quality, but face/head proportions differed from both the character images and the original person. The later M8 rigging pass cannot be assumed to restore identity already lost in this step. Hi3D's documented `scene-portraitv2.1` variant is tuned for portraits and characters. It uses four named cardinal images with the 1536pro tier, 500k target faces, textures enabled, and GLB export. No paid provider request was made during implementation; the later user-run test found better geometric likeness for one identity.

A real user-started Hi3D job returned HTTP 202 with JSON `status: IN_PROGRESS` after hundreds of five-second polls, then eventually completed. Its `status_url` matched the app's queue URL. The app logs the allowlisted queue state and shows elapsed wait time, with a long-wait explanation after ten minutes. The acknowledged job ID remains recoverable with GET-only resume; a fresh paid submit is never automatic.

The user subsequently received and visually reviewed that Hi3D output: facial and head geometry is more faithful to the approved images than the prior models, but the surfaces appear like shiny plastic. Read-only inspection of the supplied 26.3 MB GLB found one mesh, 824,172 triangles, one material, a 4096² base-color texture, and a 4096² metallic/roughness texture. The latter's occupied texels are predominantly green value 127/255 (roughness near 0.5), with metalness channel zero. The material uses one UV set for skin, hair and eyes; there are no separate semantic materials. This supports a material/lighting cause for the plastic finish, while the exact perceptual contribution of baked color highlights is not yet measured. The browser offers a reversible matte preview that ignores this roughness map and uses roughness at least 0.82, zero metalness and no clearcoat/env-map contribution. The user preferred this rendering, so it now starts enabled for every Hi3D result and can be toggled to inspect the raw appearance. It changes only in-memory Three.js materials; the original GLB and stored bytes remain intact. Region-specific skin/hair/eye materials still require the M8 preparation process and cannot be accurately inferred from this single material alone.

For future **new** Hi3D requests the selector now distinguishes the proven `1536pro` quality setting from `1536profast`, which fal documents as the portrait v2.1 fast tier. Both use the same endpoint and portrait model; the selected resolution is recorded in metadata and GET-only recovery uses the endpoint. The fast tier may reduce generation time, but speed and identity preservation have not been measured on this character. Existing jobs and downloaded GLBs keep their original settings.

Each model uses the existing explicit paid-submit action, queue recovery, GLB download, orbit review and original-asset storage. Metadata records the chosen model, the exact image URLs and request IDs actually sent, and model parameters. The page can reopen prior results from locally retained GLBs by request ID. No visual-quality claim is made until the user compares the same identity in front, both profiles, rear and top views.

For each real run, compare the front of the orbitable 3D model with the approved front image displayed beside it. Record the original person's recognizable facial geometry, especially eye spacing/shape, nose projection, cheek width, jaw/chin and head proportions. Then check crown closure, ears, hair volume, eye materials, texture consistency, request reliability and price. Use the same approved view set for comparisons where possible and note the different input counts. A valid GLB and basic bounds checks do not prove likeness. Model quality and Safari behavior remain manual checks; no paid test runs are automated.
